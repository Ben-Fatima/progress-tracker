Evaluator code-review checklist

Compressed from Lesson 0002. Re-read the morning of any AI-eval assessment.

The four lenses (in priority order)

LensHunt forCommon planted bugs
1. CorrectnessWrong output for some/all inputsOff-by-one, un-awaited Promise, null/empty edge cases, wrong operator, swallowed errors
2. SecurityInput reaching a dangerous sinkSQL/HTML interpolation, unvalidated input, exposed secrets
3. PerformanceWork scaling badly with inputQuery/network call in a loop (N+1), repeated computation, needless O(n²)
4. ReadabilityMaintainability issuesLoose equality, misleading names, dead code. Never lead with this.

The finding format

Finding → Evidence → Fix

"Line N: [what's wrong] — [mechanism that proves it / concrete consequence]. Fix: [correction]."

  • Cite the line. Name the mechanism. Give the fix.
  • "Silently returns [] for every input" beats "doesn't work."
  • Severity order in your written review: correctness > security > performance > style.

Rubric lines (Task Author)

Test every criterion: could a plausible-but-wrong solution still pass it?

  • ❌ Vague: "code is efficient" / "handles errors well"
  • ✅ Checkable: "makes exactly one DB query for any input size" / "all user input reaches SQL via bound parameters" / "returns [x] for input [y]"
  • A good criterion names: the observable behavior, the input variation, and the required output.

Assessment-day rules

  • Write in complete, plain-English sentences — your writing is the work sample.
  • Rank/compare solutions with justification, not vibes.
  • If asked to review a task prompt: check rubric checkability, reproducibility, and whether a wrong-but-plausible fix could score full marks.
