PHP: four methods

What: four methods for the stock movement controller, in the order you read them: validate, normalize, stock check, store. Where: replace the matching method in your controller. Why: together they check the input, save the signed quantity, and refuse OUT movements that would drop stock below zero.

Replace the matching method, not the whole controller. Keep existing imports, FIELDS, index and history helper.

1. validateMovement

What: checks product, location, type, quantity and note. Where: the private method below store(). Why: bad input is rejected before anything is saved.

private function validateMovement(array $data)
{
    return validator($data, [
        'product_id' => ['required', 'integer', 'exists:products,id'],
        'location_id' => ['required', 'integer', 'exists:locations,id'],
        'type' => ['required', 'string', Rule::in(StockMovement::TYPES)],
        'qty' => ['required', 'integer', 'not_in:0'],
        'note' => ['nullable', 'string'],
    ])->validate();
}

2. normalizeQtyByType

What: turns the quantity into the signed value that gets stored. IN is positive, OUT is negative. Where: the private method, called from store(). Why: the database stores the sign, so a later stock sum is correct.

private function normalizeQtyByType(string $type, int $qty): int
{
    return match ($type) {
        'IN' => abs($qty),
        'OUT' => -abs($qty),
        default => $qty,
    };
}

3. hasSufficientStockForOut

What: reads current stock and checks that an OUT movement will not make it negative. Where: the private method, called from store() only for OUT. Why: it prevents over-issuing stock.

private function hasSufficientStockForOut(int $productId, int $locationId, int $qty): array
{
    $stock = StockMovement::stockOnHand($productId, $locationId);

    return [
        'ok' => $stock + $qty >= 0,
        'stock' => $stock,
    ];
}

4. store

What: the request entry point. It validates, normalizes, runs the OUT check inside a transaction, saves the row, and returns JSON. Where: replace the existing store() method. Why: one place that ties the three helpers together.

public function store()
{
    $data = request()->only(self::FIELDS);
    $validated = $this->validateMovement($data);
    $validated['qty'] = $this->normalizeQtyByType($validated['type'], $validated['qty']);

    return DB::transaction(function () use ($validated) {
        if ($validated['type'] === 'OUT') {
            $result = $this->hasSufficientStockForOut(
                $validated['product_id'],
                $validated['location_id'],
                $validated['qty']
            );

            if (!$result['ok']) {
                return response()->json([
                    'message' => 'Insufficient stock',
                    'current_stock' => $result['stock'],
                    'requested_out' => abs($validated['qty']),
                ], 422);
            }
        }

        $movement = StockMovement::create($validated);

        return response()->json([
            'message' => 'Movement added successfully',
            'data' => $movement,
            'current_stock' => StockMovement::stockOnHand(
                $validated['product_id'],
                $validated['location_id']
            ),
        ], 201);
    });
}

Concurrency: a database transaction alone does not guarantee concurrency safety. Two requests can read the same stock before either writes. The demo requests in this guide run one at a time, so this is not tested here.

ADJUST: ADJUST keeps signed corrections as entered. The OUT availability check is not a guarantee for every movement type.

Postman: requests

What: create one demo product, one demo warehouse, then movements. Where: Postman, base URL http://127.0.0.1:8008. Why: the movement bodies need the real product and location IDs from the earlier responses.

  • Every request: header Accept: application/json. Body type raw JSON (Content-Type: application/json).
  • Send each successful movement once. Repeats change stock.
  • Save the returned data.id for each created record.
  • If a unique code is already used, change it to a new value. Do not retry blindly.

Create product

What: one demo product. Where: POST to http://127.0.0.1:8008/products. Why: its data.id is the product ID for the movements.

{"sku":"DEMO-KB-001","name":"Demo Keyboard","unit_cost_cents":10000,"min_stock":2}

Expected: HTTP 201 and data.id. Save the ID.

{"code":"DEMO-WH-001","address":"Demo warehouse"}

Expected: HTTP 201 and data.id. Save the ID.

Movements (POST)

Where: POST to http://127.0.0.1:8008/movements for every card below. Send them in this order.

1. IN 10

What: receive 10 units into stock. Why: starts the stock count.

Body hidden until both IDs are valid.

Expected: HTTP 201, data.qty 10, current_stock 10, movement count 1.

2. OUT 4

What: issue 4 units. Why: stock goes from 10 to 6.

Body hidden until both IDs are valid.

Expected: HTTP 201, data.qty -4, current_stock 6, movement count 2.

3. OUT 7

What: issue 7 units when only 6 are left. Why: shows the stock check refusing an over-issue.

Body hidden until both IDs are valid.

Expected: HTTP 422, message "Insufficient stock", current_stock 6, requested_out 7, movement count 2. No row is saved.

4. OUT 6

What: issue the remaining 6 units. Why: stock goes to exactly 0.

Body hidden until both IDs are valid.

Expected: HTTP 201, data.qty -6, current_stock 0, movement count 3.

5. IN 0

What: a zero quantity. Why: shows validation rejecting it.

Body hidden until both IDs are valid.

Expected: HTTP 422 validation error. No row is saved. The database stays at stock 0 and movement count 3.

SQL: read-only checks

DBeaver connection: it must be the same API database, db.sqlite. Not local.sqlite or testing.sqlite.

Re-run the SELECTs to refresh the results. Read the row that matches your demo product and location IDs. Do not edit grid cells.

Movement rows

What: every stored movement with its signed quantity. Where: DBeaver, run against db.sqlite. Why: confirms what was actually saved.

SELECT id, product_id, location_id, type, qty
FROM stock_movements
ORDER BY id;

Stock and count per product and location

What: movement count and stock on hand for each product and location pair. Where: DBeaver, run against db.sqlite. Why: compare with the expected counts and stock.

SELECT product_id, location_id,
       COUNT(*) AS movement_count,
       SUM(qty) AS stock_on_hand
FROM stock_movements
GROUP BY product_id, location_id;
