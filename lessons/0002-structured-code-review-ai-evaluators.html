The evaluator's toolkit (5 minutes to learn)

Skill 1 — The four review lenses

Review every snippet through exactly four lenses, in this order:

  1. Correctness
    Does it produce the right output for all inputs? Look for: off-by-one bounds, unhandled edge cases (empty array, null, single element), async values never awaited, wrong return paths.
  2. Security
    Can input reach a dangerous sink? Look for: user data interpolated into SQL or HTML, unvalidated input, secrets or internals exposed.
  3. Performance
    Does work scale with input size? Look for: a query or network call inside a loop (N+1), repeated work that could be hoisted, O(n²) where O(n) exists.
  4. Readability
    Could a teammate maintain this? Look for: misleading names, loose equality masking types, dead code, unnecessary complexity. Ranked last — never lead with style when correctness bugs exist.

Skill 2 — The finding format

Every comment you write follows one shape:

Finding → Evidence → Fix.
"Line 4: db.query() returns a Promise that is never awaited, so user.active is undefined on every iteration and the function silently returns []. Fix: await db.query(...)."

Weak reviewers write "the loop looks wrong." Evaluators write a claim, the mechanism that proves it, and the correction. That difference is the job.

Skill 3 — Checkable rubric lines (Task Author)

A rubric criterion is only good if two reviewers would score it identically. Test every criterion: could a plausible-but-wrong solution still pass it?

  • ❌ "The code is efficient." — unmeasurable.
  • ✅ "The function makes exactly one DB query regardless of userIds.length." — observable, checkable.

Recommended primary source: Google Engineering Practices — How to do a code review. The canonical industry reference for what a good review looks like and how to write comments. Skim "What to look for" before your assessment.

Exercise 1 — Review this AI-generated function

The function below was "written by an AI assistant." It should return the email addresses of all active users given a list of IDs. It contains at least 5 defects. Write your review on paper or in a scratch file — one comment per defect, in Finding → Evidence → Fix format — before opening the answers.

1  async function getActiveUserEmails(userIds) {
2    const emails = [];
3    for (let i = 0; i <= userIds.length; i++) {
4      const user = db.query(
5        `SELECT email, active FROM users WHERE id = ${userIds[i]}`
6      );
7      if (user.active == true) {
8        emails.push(user.email);
9      }
10   }
11   return emails;
12 }

Spend 10–15 minutes. Attempt every lens before revealing.

Finding 1 — Correctness

"Line 4: db.query() is async but never awaited — user is a Promise, so user.active is always undefined and the function silently returns [] for every input. This is the most severe bug: total functional failure with no error thrown. Fix: const user = await db.query(...)."

Finding 2 — Correctness

"Line 3: the loop condition i <= userIds.length iterates one past the last element, querying with userIds[undefined index] = undefined on the final pass. Fix: i < userIds.length, or better, iterate with for (const id of userIds)."

Finding 3 — Security

"Line 5: userIds[i] is interpolated directly into the SQL string — SQL injection. Any caller-controlled value can alter the query. Fix: use a parameterized query, e.g. db.query('... WHERE id = ?', [userIds[i]])."

Finding 4 — Performance

"Lines 3–10: one database query per element — the classic N+1 pattern. For 1,000 IDs this issues 1,000 round trips. Fix: batch with WHERE id IN (...) in a single query."

Finding 5 — Correctness (edge case)

"No input validation: if userIds is null or not an array, the function throws TypeError rather than returning a defined result. Fix: guard the input or document the contract."

Finding 6 — Readability (minor)

"Line 7: user.active == true uses loose equality — works by accident on truthy values but masks non-boolean data (e.g. 'yes', 2). Prefer === true or a truthiness check with intent made explicit."

Self-score: count the defects you found (max 6) and — separately — how many you wrote in Finding → Evidence → Fix format. Finding the bug but writing "loop is off" scores half. The format is half the skill.

Exercise 2 — Turn a bug into a rubric line

Task Author skill: imagine the snippet above is a task where the agent must fix it. Write one rubric criterion that verifies the N+1 fix.

Before revealing, apply the test: could a wrong solution still pass your criterion?

Model rubric criterion

"Correctness is verified by a test asserting the function performs exactly one database query when called with any userIds array, including length ≥ 2, and still returns the correct set of active-user emails."

Why it works: it names the observable behavior (query count), the varying input, and the still-required correct output — a wrong fix (e.g. caching, or fetching one fewer query) fails it cleanly.
