What this interview is actually grading

New skill to demonstrate: AI-generated code fails differently than human code. It is usually clean, idiomatic, well-named — and wrong in ways that pass the happy path. Your job in this interview is to show you hunt for plausible-but-wrong, not messy-but-right.

The evaluator's additions to your toolkit (5 minutes)

Skill 1 — The plausible-but-wrong hunt

On top of the four lenses from Lesson 0002 (correctness → security → performance → readability), add the AI-specific check:

  1. Run it mentally on hostile inputs — empty, null, single element, maximum, malformed. AI code is optimized to look right on the example given in the prompt.
  2. Check the reasoning, not just the output — a correct answer reached by wrong reasoning still needs flagging. It means the model got lucky and will fail the next variation.
  3. Check spec compliance — fluent code that solves an adjacent problem is the most common AI failure. Re-read what was actually asked.

Skill 2 — What makes a good problem + test suite

This role pays you to author problems, not just solve them. A good evaluation problem:

  • Unambiguous spec — inputs, outputs, edge-case behavior all defined. If two experts could disagree on the correct answer, the problem is broken.
  • A separating trap — one subtlety that divides strong solutions from weak ones (ordering, a boundary, a subtle invariant).
  • Checkable tests — happy path, edge cases, and at least one case that a plausible-but-wrong solution fails.

Skill 3 — Reviewing model reasoning

When reviewing a model's explanation of architecture or debugging, ask: does each step of reasoning actually support the conclusion? Conclusion-right/reasoning-wrong is a flag. Reasoning that skips justification ("obviously", "simply") is a flag.

Exercise 1 — The plausible-but-wrong hunt

An AI was asked: "Write a function that returns true if a string's brackets are balanced — (), [], {}." Its solution looks clean. Find what it gets wrong — write findings in Finding → Evidence → Fix before revealing.

function isBalanced(str) {
  const counts = { '(': 0, '[': 0, '{': 0 };
  const pairs = { ')': '(', ']': '[', '}': '{' };

  for (const ch of str) {
    if (ch in counts) counts[ch]++;
    else if (ch in pairs) counts[pairs[ch]]--;
  }
  return Object.values(counts).every(c => c === 0);
}

Trace it on "([)]" before revealing anything.

Finding 1 — Correctness (the trap)

"The function counts brackets instead of checking their order. Input "([)]" returns true — every open has a matching close — but the brackets are interleaved, not balanced. Any input where closers appear out of nesting order ("{[(])}", ")(" where the count dips negative then recovers... it also misses mid-string negatives like ")(" which nets to zero) passes incorrectly. Fix: use a stack — push openers, on each closer pop and verify it matches."

This is the textbook plausible-but-wrong failure: clean code, passes "()", "{[]}", "(()())" — fails the one case that matters.

Finding 2 — Spec ambiguity to flag

"The spec doesn't say how to treat non-bracket characters. This solution silently ignores them — "a(b)c" works by accident. Is that intended? A good evaluator flags the ambiguity in the problem statement itself, not just the code."

Finding 3 — Subtle correctness

"")(" returns true — the count goes negative then back to zero, and only the final count is checked. Order matters at every step, not just at the end. The stack fix covers this too."

Self-score: Finding 1 is the must-catch — if you found the ordering bug plus one more, you're at evaluator level. If the code looked fine to you on first read, that is exactly what this exercise exists to fix.

Exercise 2 — Write the test cases that catch it

Author skill: write a test suite for the bracket problem that a plausible-but-wrong solution cannot pass. List your cases before revealing.

Model test suite
  • "{[]}" → true — happy path, nested
  • "([)]" → false — the killer case: balanced counts, wrong order. Filters out every counting-based solution.
  • ")(" → false — wrong order at the start, nets to zero
  • "(" → false — unmatched opener
  • "" → true or spec'd — edge case; a good suite forces the spec to answer this
  • "a(b)c" → per spec — forces the non-bracket question to be resolved

The pattern: happy path, the separating trap, two edge cases, and every ambiguity in the spec converted into a test. That last part is the Task Author instinct — if the spec is silent, the test suite is where you notice.

Round 2 — Technical judgment (the differentiator)

Q2. "How do you evaluate whether AI-generated code is good?"

Model answer

"Four lenses, in order: correctness, security, performance, readability. But AI code needs a fifth instinct — it fails plausibly. It looks clean and passes the obvious example, so I run it mentally on hostile inputs: empty, null, boundary, out-of-order. I also check whether it solved the problem that was actually specified, not an adjacent one. And when the answer is right but the reasoning is wrong, I still flag it — a lucky model fails on the next variation."

Q3. "Describe a technically challenging problem you solved."

STAR format. Your stock tracker's event sourcing is the strongest story — real architectural decision, real tradeoffs.

Model answer (your real project)

"In a stock-tracking app I built, I needed inventory state that could survive audits and corrections. Instead of mutating a stock count, I modeled it as an append-only event log — every adjustment is an event, and current stock is derived by folding them. That made corrections a new event rather than a destructive update, so the history stays intact and auditable. The tradeoff was query cost — deriving state is more expensive than reading a column — which I handled by [snapshotting / accepting the cost at this scale]. It taught me that the 'correct' model is the one whose failure modes you can live with."

Why it works: real decision, explicit tradeoff, and a reflective close. Evaluators hire people who see tradeoffs, not people who claim there are none.

Q4. "How would you design a coding problem to test whether a model truly understands X?"

Model answer

"I'd write a spec that's unambiguous on inputs, outputs, and edges — then build one separating trap into it: a subtlety where the obvious approach is wrong, like counting instead of ordering in a bracket-matcher. Then the test suite does the real work: a happy path, boundary cases, and at least one case that a plausible-but-wrong solution fails. If my tests can't distinguish a correct solution from a convincing wrong one, the problem isn't finished."

Q5. Design reasoning — "How would you design a URL shortener / rate limiter / simple cache?"

60–90 seconds, structured. They're scoring shape, not completeness.

The shape to use every time

"Requirements first: what's the read/write pattern, what scale, what consistency do we need? Then components: for a rate limiter — a counter store like Redis, a windowing strategy — fixed window is simple, sliding window is fairer. Then the tradeoffs: fixed window can burst at boundaries; sliding costs more memory. Then a decision with a reason: I'd take fixed window for v1 because correctness under concurrency matters more than burst fairness at this scale."

Requirements → components → tradeoffs → decided-with-reason. Never jump to components first.
